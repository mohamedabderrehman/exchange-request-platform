## A request receipt is different from an executed exchange

This application collects an exchange request, recipient details and an optional proof image. PHP validates the submission and can send the details and photo to Telegram. The displayed conversion uses configured rates; the receipt identifies intake, not settlement or a live market transaction. Historical tracking and generated marketing activity are identified as presentation features.

That scope shapes the public demo: it accepts synthetic values and never asks an evaluator to submit real financial details. Provider credentials are server-side environment values, and former transaction records and sensitive request logs are excluded from publication.

## Treating image and message content as untrusted input

Browser-provided MIME labels are not sufficient evidence that an upload is an image. The server checks content, size and supported request fields, while cURL verifies TLS. User text is escaped before inclusion in Telegram HTML messages so input cannot change the intended formatting.

The local checks cover intake without proof, invalid amounts, unsupported currencies and forged image content. Valid proof delivery and live provider failures remain separate work before operating a real request service. The project demonstrates form UX and server processing; it does not claim automated financial execution.
